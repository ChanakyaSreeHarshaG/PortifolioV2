Q1: What is Query Folding in Power Query, why is it vital, and what breaks it? ▼

Answer: Query Folding is the ability of Power Query to translate user transformation steps into a single native query (such as native T-SQL or Snowflake SQL) and execute it on the source database server rather than pulling all raw rows into Power BI local memory.

Why it matters: Dramatically speeds up scheduled refreshes, reduces memory pressure, and is an absolute prerequisite for Incremental Refresh.

What breaks query folding:

  • Transformations on flat files (CSV, Excel) that have no native query engine.
  • Complex M functions like Table.Buffer(), custom Python/R scripts, or non-foldable index additions.
  • Applying non-foldable steps early in the query: once folding breaks, all subsequent steps must be processed in client memory.
💡 Interview Pro-Tip: Always check query folding by right-clicking the last step in Applied Steps and verifying if "View Native Query" is enabled.
Q2: What is the architectural difference between Merge Queries and Append Queries? ▼

Answer:

  • Merge Queries: Combines tables horizontally (equivalent to a SQL JOIN) based on one or more matching key columns. Supports Left Outer, Right Outer, Full Outer, Inner, Left Anti, and Right Anti joins.
  • Append Queries: Combines tables vertically (equivalent to SQL UNION ALL) stacking rows from multiple tables having matching column headers.
💡 Gotcha: If you merge wide tables in Power Query instead of creating a star schema relationship in the data model, you inflate memory consumption and lose VertiPaq dictionary compression advantages.

Q3: Why is Star Schema strongly preferred over Snowflake Schema in Power BI? ▼

Answer: Power BI's in-memory storage engine (VertiPaq) is an in-memory columnar database. In a Star Schema:

  • Dimensions are denormalized, meaning fewer table joins are needed when evaluating DAX measures.
  • VertiPaq compresses duplicate strings across columns using dictionary encoding with extreme speed.
  • In a Snowflake Schema, joining normalized sub-dimension tables introduces relationship overhead and complicates DAX filter propagation without saving meaningful RAM.
Q4: How do you handle Role-Playing Dimensions (e.g. Order Date vs Ship Date)? ▼

Answer: There are two architectural solutions:

  1. Physical Table Duplication: Create two separate date tables (DimOrderDate and DimShipDate). Simple for business users in self-service reporting, but duplicates data model size.
  2. Inactive Relationship + DAX USERELATIONSHIP (Recommended): Keep a single master DimDate table. Establish one active relationship with OrderDate and an inactive relationship with ShipDate. In DAX, activate it dynamically:
Sales by Ship Date = CALCULATE( [Total Sales], USERELATIONSHIP(FactSales[ShipDateKey], DimDate[DateKey]) )

Q5: Explain Calculated Columns vs Measures. Which consumes RAM vs Disk? ▼

Answer:

  • Calculated Column: Evaluated during data refresh row-by-row. Stored permanently inside the VertiPaq database on disk and loaded into RAM. Increases file size and refresh time. Use only when needed as a slicer or relationship key.
  • Measure: Evaluated on the fly at query time in response to user slicers and visual filter contexts. Consumes zero disk storage and releases RAM immediately after visual rendering.
Q6: What is Context Transition in DAX and when does it occur? ▼

Answer: Context Transition is the process where DAX automatically transforms an existing Row Context into an equivalent Filter Context.

It is triggered whenever CALCULATE() or CALCULATETABLE() is called within a row context (or whenever any measure is referenced inside an iterator like SUMX or a calculated column, because every measure contains an implicit CALCULATE).

⚠️ Critical Pitfall: Calling a measure in a calculated column on a table without a primary key can filter on all duplicate attribute values, leading to erroneous results.
Q7: How do you write Year-over-Year (YoY) Sales Growth % in DAX? ▼
Total Sales = SUM(FactSales[SalesAmount]) Sales SPLY = CALCULATE( [Total Sales], SAMEPERIODLASTYEAR(DimDate[Date]) ) YoY Growth % = DIVIDE( [Total Sales] - [Sales SPLY], [Sales SPLY], BLANK() )

Rules for Time Intelligence:

  • The Date table must have continuous dates with no missing days.
  • The Date table must be marked as an official Date Table in Power BI.

Q8: How do you implement Dynamic Row-Level Security (RLS) with user mapping? ▼

Answer:

  1. Create a Security Mapping table (UserSecurity) containing UserEmail and RegionID.
  2. Establish a 1-to-Many relationship between UserSecurity and DimRegion (enabling "Apply security filter in both directions" if filtering upwards).
  3. In Power BI Desktop, go to Modeling → Manage Roles, create role RegionalUser, and write the DAX filter on UserSecurity:
[UserEmail] = USERPRINCIPALNAME()

When published to Power BI Service, assign the Azure AD security group to this role. Power BI automatically filters rows matching the logged-in user's corporate email.

Q9: How do you configure Incremental Refresh and what are the prerequisites? ▼

Answer: Incremental Refresh stores historical partitions and only refreshes recent data.

Setup Steps:

  1. Define two Power Query Date/Time parameters named exactly: RangeStart and RangeEnd.
  2. Filter the fact table transaction date column using: Date >= RangeStart and Date < RangeEnd.
  3. Verify that Query Folding is active on this filter step (mandatory!).
  4. In Power BI Desktop, right-click the table and choose Incremental Refresh. Specify historical retention (e.g. 3 years) and refresh interval (e.g. past 7 days).
